# code-simplifier

## 先做这一步(不要跳过)

清单在下面,但**清单本身是弱的** —— 你在同一个上下文里自查,如果你已经相信自己找到了根因,
你会自然地把新增的分支解释成「真实的不同情况」。所以先做经验验证,再做清单:

1. 写出这次修复**声称**覆盖的输入类别,一句话。
2. 造 3 个该类别里的**语义变体**:换措辞、换语言、换顺序、加噪音、换同义实体。
   都应该被修好。
3. 造 2 个**邻近反例**:和触发条件很像但不该走这条新路径的输入。
   都应该保持原行为。
4. **实际跑一遍**,把 5 个结果贴出来。

判读:

- 变体挂了 → 你修的是一个字符串/一个 case,不是根因。回去重修,不要靠加分支补齐。
- 反例被误触发 → 新条件太宽,把不该管的输入抢走了。
- 跑不了(没有可执行入口、依赖外部服务)→ **明说跑不了**,别把清单结果当成验证过。

## 然后过清单

- 这次新增的逻辑,和现有哪个函数职责重叠?能否合并 —— 不只看同名同参,看做的事是不是一回事。
- 新加的抽象层有没有实际的第二个使用者?没有就压平。
- 新加的分支是在处理真实的不同情况,还是在给某个特例打补丁?
  自检:把这个分支删掉,失败的是**一类输入**还是**一个输入**?
- 本次净增 vs 净删。只增不删的话,旧路径为什么必须保留 —— 说得出调用方,还是「以防万一」?
- 有没有为了让流程跑通而加的 try/except,掩盖了本该暴露的错误?
- 如果改的是 prompt / 工具描述 / schema:里面有没有出现具体用户措辞(「如果用户说 X 就 Y」)?
  那和代码里的 `if "X" in query` 是同一件事,只是挪到了没有静态检查的地方。

## 输出

只写三段:

1. **验证结果** —— 5 个输入各自的实际表现,以及跑没跑成。
2. **发现的问题** —— 每条给出文件:行。没有就写「无」,不要凑数。
3. **建议的删除** —— 具体到函数名。没有就写「无」。

不要复述改动内容,我知道我改了什么。
